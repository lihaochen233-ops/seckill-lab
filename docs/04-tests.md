# 第四课：用测试证明，而不是只说“线程安全”

先看 `internal/store/contract_test.go`。`contract` 接收一个创建仓库的工厂函数，同一批业务断言分别用于 Memory 和 MySQL。接口的价值在这里体现得很直接。

## 每个实验在证明什么

| 实验 | 必须检查的结果 |
|---|---|
| 200 用户争抢 20 件 | 成功 20，订单 20，库存 0 |
| 同 key 并发 40 次抢 1 件 | 1 次创建，39 次重放，所有订单 ID 相同 |
| 同用户换 40 个 key | 仍然只有 1 张订单，只扣 1 件 |
| 同 key 用于另一商品 | 冲突，第二件商品库存不变 |
| 活动未开始/已结束 | 不产生订单、不扣库存 |
| 参数错误、已取消上下文 | 不扣库存 |
| 人为触发 INSERT 失败 | 整笔事务回滚 |
| 两个独立连接池 | 使用同一个数据库仍不会超卖 |
| HTTP 层 | 不能从请求体伪造用户；别人查不到订单 |
| Redis Lua | 100 次并发只放行 10 次，窗口过期可重新放行 |

并发测试中的 WaitGroup 等待所有 goroutine 完成；关闭 start channel 是“发令枪”，让请求尽可能集中进入，而不是慢慢顺序发出。它不是证明所有可能调度的数学证明，但比一次手点更能发现实现缺陷。

## 三种测试不能互相替代

1. 内存/业务测试：快，验证业务契约和并发逻辑。
2. MySQL 集成测试：真的创建 InnoDB 表、唯一索引、触发器，验证 SQL 和事务行为。
3. HTTP 实验：带认证、JSON、网络、连接池和端点查询的闭环。

`go test -race` 检查共享内存是否有未同步访问，不会自动判断你的 SQL 是否超卖。Redis 的测试使用 miniredis 执行 Lua，能验证脚本逻辑与过期，但不能代替真实 Redis 部署、主从切换、网络故障测试。

## 正确使用 loadtest

启动全新演示服务后运行 `go run ./cmd/loadtest -n 500 -c 32 -repeat 2`。

`-n` 为不同用户数，`-c` 为同时工作的 HTTP worker 数，`-repeat` 为每人同 key 提交次数。500 用户 × 2 次 = 1000 次请求，并不等于 1000 个同时运行的请求。

工具先取令牌与初始库存，再开始计时；批量请求结束后停止计时，再读取最终库存、查询所有成功订单。P50/P95 统计这批下单请求的客户端耗时，包含成功、重放和售罄响应。

正确性判定要求独立活动、无其他写流量、用户之前没有购买过、时间窗口有效。429 和 503 都会被计为异常，使完整验证失败；这帮助你区分“保护机制拒绝了请求”和“所有本该抢到的用户都完成了交易”。测试限流本身时，429 是预期行为。

MySQL 模式需设置与服务端相同的 `AUTH_SECRET`。想练更多轮实验，创建新活动记录后传 `-product 新ID`，或使用全新的测试库。不要删除已有订单再声称验证数据可追溯。

## 自己读一条断言

```go
stock, orders := f.audit()
if created.Load() != 20 || stock != 0 || orders != 20 {
    t.Fatalf(...)
}
```

`atomic.Int64` 让多个 goroutine 安全记录成功次数；`audit` 直接读仓库或数据库统计最终状态。响应数量和持久化订单数量都要核对，而不仅是“返回了 200”。

练习：将某个测试库存改成 7，先写出预期新建、重放、售罄数量，再运行。给“活动结束后，之前成功的 key 仍可重放”补一个测试，注意不要用脆弱的短时间 sleep。
