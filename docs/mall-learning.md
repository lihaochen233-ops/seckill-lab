# 学习顺序与第一课

先把项目跑起来并操作一遍，再读源码。目标不是背下全部目录，而是能独立解释业务规则、事务边界、并发不变量和异常恢复。

## 按重要性安排阶段

| 阶段 | 重要性 | 读哪些代码 | 必须回答的问题 | 动手练习 |
|---|---|---|---|---|
| 0：看见全流程 | 入门 | README、main.go、model.go | 商品、活动、ticket、订单分别是什么？ | 用户下单、管理员发货、用户收货 |
| 1：订单与事务 | 最高 | orders.go、schema.sql、mall_test.go | 为什么扣库存和写订单要在同一事务？为什么不用 float 算钱？ | 给订单插入制造错误，观察扣库回滚 |
| 2：幂等和状态机 | 最高 | Checkout、ChangeOrder、ticketID | 重试同一请求为何返回原订单？相同键不同参数为什么拒绝？ | 重复支付、重复退款、他人订单访问 |
| 3：秒杀准入 | 最高 | cache.go/reserveScript、worker.go/Submit | Lua 原子性解决什么？为什么 Redis 扣了还要 SQL 扣？ | 200 人抢 30 件，再改成 1000 人 |

建议先花 3～5 天掌握阶段 0～2，再用 1～2 周完成秒杀与恢复，最后补前端和部署。时间只是参考，不理解事务时不要急着研究 RabbitMQ 参数。

原 `docs/00`～`07` 是更简单的基础版课程；如果新版陌生概念太多，可以先运行 `cmd/oversell`，再读 `internal/store/mysql.go` 的基础事务，最后回到商城。

## 第一课：一次普通下单发生了什么

先看 `model.go` 的四个类型：

- `Product`：当前商品价格、库存、是否上架。
- `Address`：用户可编辑的地址。
- `Line`：浏览器提交的商品编号和数量。
- `Order`：不可随商品编辑改变的订单快照，包括成交价和收货地址。

浏览器不能告诉服务器“这件商品我只付 1 分钱”。它只提交如下数据，并在请求头携带 `Idempotency-Key`：

```json
{"address_id":1,"items":[{"product_id":1,"quantity":2}]}
```

跟着这条调用链读：

```text
Cart.vue/checkout
  → api.ts/api（携带 Cookie、CSRF、幂等键）
  → api.go/middleware（来源检查、并发上限、超时）
  → api.go/route（会话、权限、CSRF）
  → api.go/checkout（读取和校验 JSON）
  → orders.go/Checkout（真正的业务事务）
```

`BeginTx` 创建事务，后面的所有相关 SQL 都用 `tx`，不能中途改用 `d.SQL.Exec`。`defer tx.Rollback()` 是兜底清理：任何提前 return 都回滚；成功 Commit 后 Rollback 不再撤销已经提交的结果。

先锁用户行，使同一用户并发提交同一请求编号时排队检查。查到已有订单时，比较请求指纹：同内容返回原订单，不同内容拒绝。不同用户购买多个商品时按商品 ID 排序锁定，以减少反向加锁造成的死锁。

接着从数据库读价格并校验剩余库存。即便应用已经判断库存够，更新仍写 `stock >= quantity` 条件，并检查影响行数。然后保存商品与地址快照、写订单、更新购物车，最后 Commit。

假设库存只剩 1 件，两个请求同时到来：第一个获得行锁，扣到 0 并提交；第二个之后读到 0，返回售罄。如果第一个写订单失败，事务回滚，库存仍是 1，第二个可以成功。这就是你应先讲清楚的防超卖基础。

练习：找到 `TestTransactionRollbacks`。测试在数据库里安装临时触发器，让插入订单故意失败，再验证库存没少。它证明的是失败路径里的原子性，而不只是“正常情况能买到”。

学完这一课，应能自己回答：

1. 如果扣库存和写订单使用两个事务，会在哪个时间点丢库存？
2. 如果只用 Go mutex，启动两个 Go 进程后还能保护库存吗？
3. 为什么订单要保存地址和价格，而不是查询时临时 JOIN 最新商品？
4. 浏览器超时后，为什么不能直接换一个请求编号重新下单？

下一课再读 `reserveScript`，把普通事务知识应用到“先准入、后异步下单”的链路上。

## 简历怎么写

在你已运行、学习并能独立解释后，可以写：

> PULSE 高并发秒杀商城：基于 Go、Vue 3、MySQL、Redis、RabbitMQ 实现单商家交易闭环。通过 Lua 原子准入、事务 Outbox、发布确认与幂等消费实现异步秒杀；设计超时关单、预扣租约补偿及 epoch 库存重建，使用并发实验和数据库故障注入验证防超卖与库存守恒。

面试展示时注明哪些是指导下实现、哪些是自己改进。只有实际运行过完整环境和压测工具，才能填写对应中间件测试结果与性能数字。本机已有“真实 MySQL + 模拟 Redis”的 1000 用户争抢测试，不应写成“1000 QPS”或“RabbitMQ 全链路压测”。

亮点讲解选两个就够：一是 DB 与 MQ 为什么需要 Outbox；二是补偿与迟到请求竞争时，墓碑和 epoch 如何防止多返库存。能画出失败时间线，比罗列十个技术名词更有说服力。
