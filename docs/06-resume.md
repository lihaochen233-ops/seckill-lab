# 第六课：怎样把项目写进简历

建议项目名：**Go 秒杀下单与并发一致性实验系统**。这是个人学习项目，写清背景，比包装成公司的线上商业系统更能经得住追问。

先完成前四阶段并自己修改过代码，再按你确实能讲清楚的部分选择表述：

> 使用 Go、MySQL 构建秒杀下单服务，完成活动商品展示、身份校验、限购、订单创建与查询；通过 InnoDB 事务、行锁、条件扣库存和联合唯一索引控制超卖与重复购买。
>
> 设计用户级幂等请求编号，支持响应丢失后的原请求重试；使用事务回滚保证订单写入失败时库存不被消耗。
>
> 编写并发、跨连接池和故障注入测试，并开发 HTTP 验证工具核对库存守恒、订单数量与重放行为；通过 500 用户、32 并发、1000 请求的本地实验验证 100 件库存仅生成 100 张订单。

学完限流后可追加：

> 使用有界并发和 Redis Lua 固定窗口限流保护下单链路，提供健康检查、请求超时、优雅退出及 Prometheus 格式计数指标。

最后一条的真实 Redis 部署仍需你亲自完成验证；本机当前只运行了脚本模拟测试。不要把未完成的部署写成线上运行经验。

## 面试中最容易被追问的六个问题

**1. 不使用 Redis 扣库存，能防超卖吗？**

可以。所有实例通过同一 MySQL 主库，库存判断和扣减受行锁/条件 UPDATE 保护，并与订单 INSERT 在同一事务完成。Redis 不是防超卖必需条件；它可以用于性能优化，但会引入额外的一致性问题。

**2. 你为什么既用 FOR UPDATE，又用条件 UPDATE？**

显式锁让订单检查、价格读取和库存修改按同商品串行进行，便于推理；`stock > 0` 是 SQL 中的必要前提防护。当前实现偏向可读与可验证，额外查询和热点锁会限制吞吐，不是最少 SQL 的极限优化。

**3. 重复购买和请求重试有区别吗？**

同 key 同商品是重试，返回同一订单；不同 key 同商品是第二次购买，限购拒绝。由两组不同的联合唯一约束兜底。

**4. 数据库已经提交，但客户端超时怎么办？**

客户端保留原 key 重试；如果已提交则返回原订单。服务不能仅凭网络错误断言这笔交易没有发生。

**5. 怎么证明没超卖？**

检查订单数、库存守恒、每用户每场唯一以及故障回滚，而不仅是无负库存。展示实际测试和可复现实验，再说明它们覆盖的场景与边界。

**6. 最大瓶颈在哪里，下一步怎么优化？**

热商品集中竞争一条数据库记录，事务串行且同步写盘限制吞吐。先度量锁等待和延迟，再考虑入口限流、缩短事务或库存分桶。Redis 预扣 + MQ 是更大的架构升级，必须补偿、去重、处理崩溃恢复，不能只加两个组件名字。

## 不要照抄的表述

- “百万并发、十万订单 QPS”：当前没有对应证据。
- “线上零故障、绝对一致”：个人本地实验不能支撑这种承诺。
- “实现 Redis + MQ 异步下单”：当前版本没有此功能。
- “独立设计开发了全部功能”：代码由助手协助完成，应能如实解释自己的学习、验证、修改和贡献。

给自己保留一项可展示的改进，例如补一类故障测试、实现列表分页或新增活动管理命令。把修改前的问题、实现与验证记录下来，这会形成你真正能讲述的项目经历。
