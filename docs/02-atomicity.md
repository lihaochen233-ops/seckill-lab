# 第二课：库存没有负数，为什么仍然超卖

初始库存 1，两人同时读取并分别写回：

| 时间 | 用户 A | 用户 B | 数据库存储的库存 |
|---|---|---|---|
| 1 | 读取库存=1 | | 1 |
| 2 | | 读取库存=1 | 1 |
| 3 | 判断有货，写库存=0，创建订单 | | 0 |
| 4 | | 用旧值判断有货，写库存=0，创建订单 | 0 |

最终库存是 0，但订单有 2 张。**超卖判断不能只看库存有没有小于 0，还要检查初始库存 = 当前库存 + 已售数量。** 本项目每张成功订单恰好一件，所以已售数量就是订单数。

运行 `go run ./cmd/oversell`。它故意用 WaitGroup 保证双方都先读到 1，这样每次都能复现，不依赖运气或 `time.Sleep`。

注意：错误实验每次读写都加了 mutex，所以未必会被 `-race` 报警。数据竞争检查关注未同步的内存访问；业务竞态关注“几步组合起来是否仍然正确”。二者不同。

## 内存版如何修复

`internal/store/memory.go` 的 `Buy` 开头：

```go
m.mu.Lock()
defer m.mu.Unlock()
```

持锁期间完成所有步骤：

1. 检查是否已经处理这个 key；是则返回原订单。
2. 查活动、检查此用户是否已经买过。
3. 检查活动时间和库存。
4. 生成订单，库存减一，保存订单和去重索引。

这整块是临界区。另一个 goroutine 必须等锁释放才能进入，因此无法在步骤 3 和 4 中间插入一次新的读取。

`defer` 把解锁注册到函数退出时执行，所以提前 `return` 也会解锁。带 mutex 的结构体不应在使用后复制，因此仓库用指针传递。

为什么没有用 `sync.Map`？它只保证单个 map 操作并发安全，并不能让“检查库存 + 写订单 + 修改三个 map”自动成为一个原子整体。

## 为什么内存版不能直接部署多个实例

两台进程各有一个 mutex、各有 100 件库存，都可能卖出 100 件。A 的锁并不能锁住 B。MySQL 的行锁由所有实例共同访问的数据库管理，才是下一阶段跨进程的同步依据。

练习：把错误实验改成锁覆盖读取到创建订单的完整过程，并移除锁内的双方读取屏障（否则两人互等会死锁）。结果应该变为一单、库存零。不要修改正式服务来制造超卖。
